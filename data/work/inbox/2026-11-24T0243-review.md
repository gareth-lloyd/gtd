  ### Verdict

  The primitive (goal, guardrails, permissions, evals, pinned model) and the three boundary rules (split read from external write, one writer per dataset, agents may reject work) are sound and worth agreeing on. The doc is weakest where it matters most: its own agent list contradicts the "domain, not workflow" rule, and the orchestration section argues for dynamic swarms without evidence, failure modes, or an ask.

  ### Main points to raise

  1. The agent table contradicts the boundary rule. The doc says boundaries follow business domains, not workflow. But Investigation, Coding, Prototyping, Spec reviewer and Eng Design reviewer are workflow stages or capabilities. None is a business domain like payments or check-in. Product Analytics and Customer Support are the only rows that read as domains. The doc needs to define "domain", or admit the split is by capability and permission set, which is what the table actually shows.

  2. Golem breaks the doc's own safety rule. The rule: wide production read must not combine with write to external-facing systems. Golem has read access to all production systems plus PR creation, and it takes tickets that carry customer-written text. A PR is a write channel that ends in production. The doc should say why that is acceptable (human review and CI as the gate) or narrow Golem's read access.

  3. Permission boundaries do not stop data crossing between agents. Customer Support has "minimal access to avoid cross contamination", but it will consume Workup's hand-off, which is built from full production read. The contamination travels in the hand-off. The doc needs a rule for what may cross an agent-to-agent hand-off, not only what each agent can reach directly.

  4. "One writer per dataset" needs a granularity. In Linear, Workup writes labels and the hand-off, Golem writes status and comments, and people write everything. The rule only works per artifact or per field. It should also say where human writers fit.

  5. Rejection has no stopping rule. Agents rejecting each other is right, but the doc gives no retry cap, no arbiter, and no escalation to a person. Under dynamic orchestration that is an unbounded loop with a cost attached. Rejections should also be logged as an eval signal for the caller.

  6. The orchestration section skips the middle option. It presents static (the task is baked into the agent) against dynamic (a platform assembles a swarm). The missing third option: fixed workflows written in code that call reusable domain agents. That gives the reuse the doc wants while keeping the debuggability, cost control and accountability that a dynamic planner gives up. Workup and Golem are static today and the doc holds them up as good examples, so "static breaks the domain rule" is overstated.

  7. The dynamic claims are unsupported. "Far larger and more diverse tasks can be handled with high quality results" has no evidence behind it. Nothing covers failure modes, cost, tracing a bad outcome to an agent, or who is accountable for a swarm's output.

  8. The doc ends without an ask. The Orbital callout reads like a lead-in to a proposal, but none follows. Is this proposing to adopt Orbital, evaluate it, or build something? What decision does the reader owe?

  ### Smaller points

  - "Agents need a consistent model" is right, but models get retired. The real rule is that a model change must pass the agent's evals first. Same for permissions: evals should gate any widening of write access.
  - The "Claude session with a system message and MCP" callout undersells the definition above it, which also requires evals and guardrails.
  - Nest's Permissions cell is cut off ("Can ask questions of"). Spec reviewer's is blank.
